# Итерация 36: пространственное прореживание богатого development-поля

На `wm_r_134291495` подтверждена непосредственная причина **26 из 192**
неуспешных попыток: cluster-buster tetra3 оставляет менее четырёх источников.
Это не нехватка видимых звёзд на фотографии. Однако **166 остальных попыток**
имеют достаточно источников для построения четвёрок и завершаются `NoMatch`.
Прореживание не объясняет полный отказ. Алгоритм распознавания не изменён;
улучшение solve rate не заявляется.

## Наблюдения и границы диагноза

После отрицательного результата [итерации 35](robustness-iteration-35.md)
исследован другой development solver-кадр — богатое поле над Маунакеа.
Повторно просмотрены сохранённые overview и crops из итерации 1
(`prototype/artifacts/robustness-iteration-1/review-final/`). Видны многочисленные
звёзды, Млечный Путь, яркий горизонт и передний план справа снизу. У ряда
источников вытянутый профиль; среди первых детекций присутствует рельеф.
Прежняя оценка 22 звездообразных источников из 24 сохраняется как визуальная,
а не как подтверждение каталоговых идентичностей.

Полноразмерные списки сильно смещены к боковым краям: **28 из первых 30**
лежат в суммарных 40% ширины, то есть при `x < 0.2W` либо `x >= 0.8W`.
Широкий bounding box поэтому не доказывает равномерный пространственный охват.

а не измерена на растянутых обзорных crops. Показатель не устанавливает
причину смещения рангов и не заменяет проверку каждой звезды.

Гипотеза R10/R11: ранжирование предоставляет поиску слишком мало разнесённых

## Внешняя привязка

Сохранённый `robustness-baseline/wcs-run/wm_r_134291495/reference.json`
имеет статус **unresolved**. Downsample 4 завершился без WCS, downsample 2
достиг wall timeout. Сохранённые `.axy` являются списками источников, а не
подтверждёнными соответствиями. Нет WCS-кандидата, по которому можно проверить
идентичности, края и распределение соответствий. Независимая геометрия и
ground truth отсутствуют; новый тяжёлый WCS-прогон не запускался.

## Зафиксированная проверка

Использован существующий `tetra3_internal.py` из итерации 4. Он копирует
проверенный по SHA-256 tetra3 0.8.0 в изолированный стенд и добавляет
наблюдательные hooks. Hook `thinning` записывает реальные индексы источников,
оставшихся после cluster-buster, для каждого проверяемого FOV. Никакой новой
реализации прореживания нет. В копии standalone caller снят только старый
фильтр имён случаев, ограничивавший его предыдущими примерами. Production,
реестр Cargo и lockfile проекта не изменялись. Старые hooks для конкретной
каталоговой четвёрки не используются для выводов о новом кадре.

Входы — первые 40/50 детекций четырёх сохранённых диагностических списков
итерации 1: координаты, flux и порядок без изменений. Преобразование в
center-origin совпадает с production, включая преобразование в f32.
Воспроизводятся восемь прежних диапазонов поиска и префиксы
`8,10,12,16,20,30`, по 48 вызовов на список. Сохраняются базы, FOV sweep,
match radius 0.01, threshold 1e−3 и timeout 2500 ms на вызов.

Дополнительный положительный контроль — сохранённые 40 детекций
`wm_r_112929230` (development), также 48 вызовов. Стенд проходит все вызовы,
даже после получения кандидата: это диагностический replay, не воспроизведение
времени полного production pipeline с ранним завершением.

Код, входы и критерии закреплены в protocol до первого запуска; binary hash
записан после сборки. Всего 240 вызовов, wall limit 180 s. Критерии:

1. Все 192 статуса целевого кадра совпадают **по порядку** с control-логом
   итерации 24.
2. Положительный контроль возвращает хотя бы одного tetra3-кандидата.
3. Все попытки имеют однозначно привязанные thinning-события; сохраняются
   реальные индексы и FOV, включая случаи менее четырёх источников.
4. Не приписывать replay новую WCS, независимую геометрию или улучшение.

## Результат

Все критерии воспроизведения выполнены:

| Список | До: NoMatch / TooFew | Повтор: NoMatch / TooFew | FOV с ≥4 источниками / все FOV | Источников после прореживания при k=30 | Время вызовов, s |
|---|---:|---:|---:|---:|---:|
| 1600 default | 48 / 0 | 48 / 0 | 1560 / 1560 | 10–11 | 2.639 |
| 1600 deep | 48 / 0 | 48 / 0 | 1560 / 1560 | 9–10 | 1.901 |
| 6016 default | 35 / 13 | 35 / 13 | 1137 / 1560 | 6–7 | 0.277 |
| 6016 deep | 35 / 13 | 35 / 13 | 1137 / 1560 | 6–8 | 0.344 |

В обоих native-списках при k=8 для всех **260 FOV** остаются ровно три
источника, с нулевыми индексами `[0,1,2]`. При k=10 остаются 3–4;
достаточно источников только в трёх dense-диапазонах (97 FOV на список).
При k=12 и выше каждая попытка имеет достаточно источников хотя бы для
одной четвёрки, но кандидат не возвращается. В сумме **5394 из 6240 FOV**
целевого кадра проходят проверку минимального числа источников.

Это установление этапа отказа: целевой кадр не доходит до проверки и LM
Starglyph, поскольку tetra3 не возвращает кандидата. `NoMatch` не раскрывает,
отвергнуты ли конкретные четвёрки при поиске в базе или внутренней проверке
tetra3. Число итоговых inliers здесь **не определено**, а не измерено как ноль.

Положительный контроль: 45 `NoMatch`, два кандидата (7 и 11 соответствий),
один `Timeout` — dense 16–30°, k=30, 2500.07 ms, уже после первого кандидата
в bootstrap 60°. Это наблюдение полного диагностического перебора, не новая
регрессия production. У целевого кадра таймаутов нет. Весь процесс занял
13.926 s, сумма matcher-вызовов цели — 5.161 s, контроля — 6.564 s;
оставшееся время включает загрузку баз и накладные расходы. Время с trace
не является производительным benchmark.

Из `prototype/`, задав путь к установленному исходнику tetra3:

```sh
export PYTHONPATH=artifacts/robustness-wcs-python:eval
export ITERATION_OUT=artifacts/robustness-iteration-36-replay
export TETRA3_SOURCE=/path/to/cargo/registry/tetra3-0.8.0
python3 eval/robustness_thinning_trace.py prepare --out-dir "$ITERATION_OUT" --registry "$TETRA3_SOURCE"
python3 eval/robustness_thinning_trace.py build --out-dir "$ITERATION_OUT"
python3 eval/robustness_thinning_trace.py run --out-dir "$ITERATION_OUT"
python3 eval/robustness_thinning_trace.py summarize --out-dir "$ITERATION_OUT"
python3 -m unittest discover -s eval -p 'test_*.py'
```

Prepare требует сохранённых исходных артефактов, перечисленных в protocol.
Опубликованный input содержит все списки для matcher replay; raw trace
позволяет проверить происхождение компактных результатов. Абсолютные пути
баз в input нужно адаптировать для другого checkout до нового замораживания.

Пройдены **248 Python-тестов**, включая split/freeze guards и привязку trace,
и сборка изолированного Rust-стенда. Production Rust не менялся, поэтому
повторные полные solver/UI gates не запускались. Отрицательные примеры и
остальные успешные кадры здесь не переизмерялись: алгоритмического варианта
нет. Manifest, опубликованный baseline и WCS-review проверены по хешам и
не изменены. Holdout не использовался.

## Следующий шаг

Проверить пригодные звёзды в центральной части **того же development-кадра**:
сопоставить их с полным списком детектора и установить, теряются ли они при
детекции, фильтрах формы или ранжировании. Только после этого фиксировать
один вариант отбора с прежним числом источников и бюджетом поиска. Простое
отключение cluster-buster пока не обосновано: оно не устраняет 166 `NoMatch`
и меняет число перебираемых четвёрок. До автоматического варианта отрицательные
примеры, успешные development-кадры и независимая проверка нового решения
остаются обязательными последующими проверками.
