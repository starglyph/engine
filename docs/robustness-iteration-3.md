# Итерация устойчивости 3: каталог и доступность паттернов

2026-10-03, продолжение [итерации 2](robustness-iteration-2.md).
Исследуется только development `wm_r_161606532`; прежний успешный
`wm_r_112929230` служит контролем диагностического инструмента.
Новых снимков, WCS-прогонов и запусков holdout нет.

**Автоматическое улучшение не подтверждено.** Установлена потеря конкретной
яркой каталожной опоры и её влияние на доступность четвёрок в сохранённой базе.
Однако адресное восстановление этой опоры не устранило отказ. Производственный
алгоритм в этой итерации не меняется; экспериментальные флаги прошлых итераций
остаются выключенными по умолчанию.

## Гипотеза и границы проверки

После возврата части источников в итерации 2 кадр всё ещё не распознавался.
Проверяем, теряются ли подходящие каталожные четвёрки из-за состава и порядка
детекций, либо поиск уже возвращает кандидата, который отклоняет проверка
Starglyph. Сначала проверяем идентичность опор; наличие внешнего WCS само по
себе не делает их правильными.

Нормализованное изображение — 4080×3072, уменьшенное — 1600×1205. Небо занимает
верхнюю часть; в нижней преобладает освещённая растительность. В уменьшенном
default среди первых 30 детекций опознаны только девять опор расширенного
набора, в deep — двадцать. Неопознанная детекция не объявляется автоматически
ложной: часть находится на растительности, часть требует отдельного разбора.

Исходные manifest, split/track, пиксели, опубликованный baseline и WCS-review
не изменялись. Входы и код фиксируются SHA-256 перед итоговыми replay.

## Проверка внешнего кандидата

Использован сохранённый `downsample-4/field.wcs` и его `.corr`, без нового
`solve-field`. Все 67 ссылок `index_ra/index_dec` сопоставляются с HYG в радиусе
5″ и относятся к звёздам ярче 6.5 mag. Это проверка каталожных ссылок, **не**
доказательство, что каждый `field_x/field_y` измеряет указанную звезду.

На исходном изображении и кропах проверены сочетание Antares–Alniyat–Paikauhale,
Rho Oph, звёзды Libra и источники у левого, правого и верхнего краёв видимого
неба. Красноватый яркий Antares и относительное расположение соседних опор
согласуются с предложенными идентичностями. Нижние строки `.corr` 61/64/66
по-прежнему попадают на растительность; неоднозначные 1/10/22/31 не возвращены
в исходный набор 56 проб.

Дополнительно спроецированы звёзды HYG ≤6.8 mag, отсутствующие в `.corr`, в
консервативной верхней области `24 < x < 4056`, `24 < y < 900`. Получена 51
каталожная запись. На кропах видны источники около предсказаний, в том числе
π Sco / Fang (HYG 78029), ω¹ Sco (78693), δ Sco / Dschubba (78165), λ Lib
(77575), ι¹ Lib (74164). Это дополнительная проверка по звёздам, не входившим
в опубликованный список соответствий внешнего решения. Их позиции всё равно
предсказывает проверяемый WCS: абсолютная независимость здесь не заявляется.

Есть близкие компоненты, например Acrab/Acrab B и Guniibuu/Guniibuu B.
51 запись нельзя считать 51 независимо разрешённой звездой. При аннотации
детекций сохраняются все соседние ID в радиусе 12 исходных пикселей; для
неоднозначной смеси без прежней компонентной ассоциации выбирается ярчайшая
возможная компонента. Такие идентичности остаются условными. Приоритет имеют
ассоциации прежней трассы компонент.

Итого расширенный набор содержит 107 каталожных ID, из них 82 входят в
mag≤6.5 базы. Остальные 25 слабее рабочего ограничения. Совпадения в видимом
небе поддерживают гипотезу о правильной области неба; геометрия всего кадра,
особенно закрытая нижняя часть, этим не подтверждается. **WCS остаётся pending,
принятого ground truth нет.**

## Что находится в реальных базах

Исследовательский Rust-тест читает существующие `.bin` напрямую через
`SolverDatabase::load_from_file`; новые базы не генерируются. В каждой 8920
каталожных записей. Выгружаются реальные четвёрки ID и участие каждой опоры,
а не число теоретически возможных сочетаний.

| База | Все сохранённые паттерны | Внутри прежних 56 ID | Внутри расширенных 107 ID |
|---|---:|---:|---:|
| bootstrap 10–70° | 941681 | 400 | 1185 |
| dense 16–30° | 7391287 | 632 | 2610 |
| dense 30–54° | 2438015 | 0 | 18 |
| dense 48–88° | 943786 | 0 | 0 |

Само наличие звезды в HYG не означает, что нужная четвёрка вошла в базу.
Результаты ниже — **принадлежность ID до внутреннего разреживания tetra3**,
проверок отношений рёбер, позы и вероятности. Положительное число не означает
доступный геометрически правильный кандидат.

Для исходных детекций после расширенной аннотации, максимальный префикс 30:

| Ветка | Полный список | Опознаны в полном списке / первых 30 | Четвёрки bootstrap / dense 16–30 / dense 30–54 |
|---|---:|---:|---:|
| 1600 default | 40 | 10 / 9 | 0 / 0 / 0 |
| 1600 deep | 50 | 35 / 20 | 0 / 0 / 0 |
| 4080 default | 40 | 36 / 28 | 49 / 143 / 0 |
| 4080 deep | 50 | 30 / 27 | 14 / 85 / 0 |

В уменьшенных списках отсутствуют сохранённые четвёрки из опознанных звёзд
этого поля. В полноразмерных списках отсутствие **всех** паттернов причиной
назвать нельзя. В коде tetra3 уже есть разреживание близких источников, перебор
FOV и собственная вероятностная проверка: они не реализуются заново и их
пороги не меняются.

## Конкретная потеря: δ Sco

Все 18 четвёрок расширенного поля в dense 30–54° содержат Dschubba, HYG 78165,
mag 2.29. Это яркий видимый источник около `(2606, 411)` исходного кадра,
отсутствующий в старом `.corr`. Новая адресная трассировка показывает:

| Ветка | Площадь компоненты | Измеренная площадь после обработки ядра | Концентрация | Причина потери |
|---|---:|---:|---:|---|
| 1600 default | 95 | 95 | 1.927 | концентрация < 2.5 |
| 1600 deep | 71 | 71 | 1.506 | концентрация < 2.5 |
| 4080 default | 555 | 212 | не вычислялась | площадь |
| 4080 deep | 382 | 212 | не вычислялась | площадь |

Это потеря **до ранжирования/top-K**, а не вытеснение более яркой растительностью.
Однако из неё не следует, что достаточно увеличить максимальную площадь:
у фильтра есть задача отбрасывать другие крупные источники, а альтернативные
пути поиска через bootstrap остаются.

## Контролируемый эксперимент

Добавлен только `cfg(test)`-модуль `solve::catalog_replay` и Python-инструменты
подготовки/сводки. У поиска и проверки отдельные списки. Поза выводится по
индексам **поискового** списка, затем `match_predictions` получает неизменный
полный исходный список детекций данной ветки. Иначе изменение числа детекций
само изменяло бы статистическую проверку.

Сохранены действующие слепые попытки bootstrap и три dense-полосы, префиксы
8/10/12/16/20/30 с прежним ограничением по длине списка, 2500 ms на вызов tetra3,
радиус/пороги принятия Starglyph. Внешняя поза и FOV в поиск не передаются.
Для коротких списков число уникальных попыток меньше. Полный исследовательский
процесс дополнительно ограничен 240 s; загрузка/обход базы учитывается отдельно
от времени matching каждого случая. Проверяется кандидат **до refinement**.

Проверены три последовательные диагностические стадии:

1. Прежние 56 опор: исходный список; только выбранные видимые опоры; те же
   опоры в каталожном порядке; доступные измеренные центроиды этих проб,
   включая отфильтрованные, в каталожном порядке. Четыре scale/tier, 16 replay.
2. Расширенные идентичности: исходный список; только опознанные выбранные
   источники; те же источники в каталожном порядке. 12 replay. Координаты
   детекций не меняются; каталожный порядок задаётся убывающей искусственной
   mass, поскольку tetra3 сортирует по ней.
3. Адресное восстановление δ Sco в двух полноразмерных списках: её измеренный
   центроид берётся из уменьшенного default и масштабируется с сохранением
   центров пикселей. Источник принудительно ставится первым; это вмешательство
   одновременно в состав и приоритет, **не автоматическая эвристика**.
   Проверяющий список остаётся исходным и не содержит возвращённую точку.
   Вместе с двумя контролями — 4 replay.

Во всех **32 replay отказ**: tetra3 не вернул кандидата. При адресном возврате
δ Sco число четвёрок dense 30–54° в первых 30 источниках растёт 0→3 в full
default и 0→1 в full deep, но решения по-прежнему нет. Уменьшенные default/deep
отказы воспроизводятся и после удаления неопознанных источников. Таймаутов
попыток и ошибок процессов нет. Все исходы, длительности, размеры списков,
счётчики `NoMatch`/`TooFew`, покрытие каждого префикса и происхождение входов
сохранены в [машиночитаемой сводке](experiments/robustness-iteration-3-diagnosis.json).

Эти 32 запуска относятся к одному снимку, а не к 32 независимым примерам.
Время диагностическое; ускорение распознавания по нему не заявляется.
При отсутствии кандидата inliers и качество геометрии решения — `null`.
Различить внутренние отказы tetra3 после наличия подходящего состава
(отношения рёбер / оценка позы / собственная проверка / refinement tetra3)
по текущему результату `NoMatch` нельзя. Ослабление внешнего acceptance
Starglyph здесь не помогло бы: до него ни один кандидат не дошёл.

## Проверки и ограничения

[Машиночитаемый протокол проверок](experiments/robustness-iteration-3-checks.json)
содержит хеши кода, результата и защищённых исходных файлов.

- Положительный контроль `wm_r_112929230`: сохранены 11 verification hits,
  RMS 1.165578 px и log-odds 23.729874 до refinement. Это воспроизведение
  прежнего результата, не независимая сертификация его геометрии.
- Исследовательский replay совпадает с производственным matcher на этом
  положительном контроле и четырёх исходных ветках `wm_r_161606532`.
- Отдельный тест переставляет проверяющий список и затем делает его пустым:
  поза сохраняется, а hits в пустом списке становятся нулём. Это защищает от
  ошибочного применения индексов поиска к проверяющему списку.
- 97 обычных Rust-тестов core пройдены; шесть исследовательских/нагрузочных
  тестов штатно ignored. Адресные исследовательские проверки запускались явно.
  11 Python-тестов `test_robustness*.py` пройдены, включая три новых контроля
  split, неизменности verification и неполной четвёрки.
- `cargo fmt --all --check`, Clippy core all-targets `--no-deps -D warnings`
  и проверка diff проходят. Строгий Clippy с проверкой зависимостей сначала
  остановился на существующем `too_many_arguments` в `simulator-core/dataset.rs`;
  несвязанный код не менялся.

Производственный путь не изменён, поэтому новые результаты всей development
и отрицательных кадров в этой итерации не заявляются. Актуальные измерения
24/34 solver и 8/8 корректных development-negative отказов относятся к
[итерации 2](robustness-iteration-2.md), как и выполненные там три regression
gates. Повторять их для отдельного `cfg(test)`-инструмента оснований нет.
Единственный holdout-negative по-прежнему не позволяет оценивать частоту
ложных принятий; holdout здесь не открывался для диагностики и не запускался.

## Воспроизведение

Нужны локальные нормализованные фото, HYG, четыре уже готовые базы, сохранённые
WCS-артефакты и `robustness-iteration-2/diagnosis-final`. Последнюю трассу можно
восстановить командами из отчёта итерации 2. Python-подготовка требует NumPy,
Astropy и Pillow; новые зависимости приложения не добавлены.

Из `prototype/` собрать тесты; путь исполняемого файла напечатает Cargo:

```bash
cargo test -p starglyph-core --release --lib --no-run --locked --offline
```

Далее из корня репозитория (`RESEARCH_BIN` — напечатанный путь с префиксом
`prototype/`; суффикс Cargo зависит от сборки):

```bash
ITERATION_OUT=prototype/artifacts/robustness-iteration-3-reproduction
python3 prototype/eval/robustness_catalog.py "$ITERATION_OUT"
python3 prototype/eval/robustness_catalog.py "$ITERATION_OUT/expanded" --expand-from "$ITERATION_OUT"
python3 prototype/eval/robustness_catalog.py "$ITERATION_OUT" --prepare-support
STARGLYPH_TRACE_INPUT="$ITERATION_OUT/expanded/trace-input.json" \
STARGLYPH_TRACE_OUTPUT="$ITERATION_OUT/expanded/traces.json" \
  "$RESEARCH_BIN" --ignored --exact solve::replay::source_traces
python3 prototype/eval/robustness_catalog.py "$ITERATION_OUT/restore" --restore-key-from "$ITERATION_OUT/expanded"
python3 prototype/eval/robustness_catalog.py "$ITERATION_OUT" --run-binary "$RESEARCH_BIN"
python3 prototype/eval/robustness_catalog.py "$ITERATION_OUT/expanded" --run-binary "$RESEARCH_BIN"
python3 prototype/eval/robustness_catalog.py "$ITERATION_OUT/restore" --run-binary "$RESEARCH_BIN"
STARGLYPH_CATALOG_INPUT="$ITERATION_OUT/positive-input.json" \
STARGLYPH_CATALOG_OUTPUT="$ITERATION_OUT/positive-replay.json" \
  "$RESEARCH_BIN" --ignored --exact solve::catalog_replay::catalog_patterns_and_replay
python3 prototype/eval/robustness_catalog_report.py "$ITERATION_OUT" --output "$ITERATION_OUT/compact.json"
```

Для `control_matches_production` используются те же `STARGLYPH_CATALOG_INPUT`
и `STARGLYPH_CATALOG_OUTPUT`, указывающие на соответствующий готовый результат.
`separate_verification_preserves_pose_and_uses_full_list` запускается с
`positive-input.json`. Все реальные исследовательские запуски явно ignored;
обычный `cargo test` не начинает обход коллекции.

Локальные полноточные JSON, логи и кропы находятся в
`prototype/artifacts/robustness-iteration-3/`; итоговые измерения — файлы
`replay-final.json`, с предшествующими `freeze-final.json` и статусами
`run-final.json`. Предварительные `replay.json` не входят в основные цифры.
Компактная сводка округляет числа до шести знаков и сохраняет хеши оригиналов.

Следующий обоснованный шаг — адресная трасса внутреннего tetra3 на уже
доступной полноразмерной четвёрке с известными ID: установить конкретный
внутренний барьер. Текущие данные не обосновывают ни общее расширение каталога,
ни изменение лимита площади, ни ослабление принятия. Проверять новую
автоматическую эвристику и затем holdout следует после такой локализации.
