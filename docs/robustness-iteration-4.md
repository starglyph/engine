# Итерация устойчивости 4: границы кадра при проверке tetra3

2026-10-03, продолжение [итерации 3](robustness-iteration-3.md).
Диагностический пример — development `wm_r_161606532`; контроль инструмента —
прежний успешный `wm_r_112929230`. Новые фото и внешние WCS не получались.

**Причина конкретного отказа подтверждена:** звёзды за границами кадра
вытесняли видимые опоры из ограниченного списка внутренней проверки tetra3.
Один автоматический патч увеличил число решений development **24→25 из 34**
и holdout **7→9 из 20**, сохранив все прежние успехи и отказы на negative.
Геометрия нового development-решения проверена на опорах вне входа решателя;
для двух новых holdout-решений внешних подтверждённых привязок нет.
Патч остаётся экспериментальным, основной pipeline не переключён.

## Подтверждённый механизм отказа

После отрицательных replay предыдущей итерации исследован внутренний путь
текущей зависимости tetra3 0.8.0. В локальную копию добавлена только трассировка;
Cargo registry, рабочие зависимости и основной Cargo.lock не меняются.
Входы — исходные полноразмерные списки default/deep, реальные сохранённые базы,
прежний порядок FOV и префиксов. Правильные каталожные ID используются только
для отбора событий в логе, не для управления поиском.

Четвёрка HYG `[73486, 74164, 76644, 78029]` сохраняется после разреживания,
находится в индексе, проходит отношения рёбер и даёт согласованное соответствие
источников и позу. Отказ происходит внутри `verify_attitude`, до внешней
проверки Starglyph. Это конкретизирует прежний неразличимый `NoMatch`.

Внутренняя проверка получает звёзды из широкого кругового запроса. После
проекции отбрасываются только точки позади камеры. Затем остаются первые
`2 × число входных центроидов` звёзд в порядке яркости каталога. Прямоугольные
границы сенсора до этого ограничения не применяются: яркие звёзды за кадром
вытесняют видимые опоры. В одной исходной попытке с FOV 35.2° из 60 оставшихся
звёзд 32 находятся вне сенсора (30 — даже с допуском сопоставления); две звезды исходной четвёрки занимают
позиции 77 и 94 (индексация от нуля) до ограничения и теряются. Это не потеря детекций на
растительности и не отсутствие нужной четвёрки в базе.

Исходная трасса двух веток содержит 96 вызовов, 3120 событий разреживания по
FOV и 140 проверок выбранной правильной четвёрки. Все эти проверки отклонены;
максимум — шесть соответствий. Наблюдательный инструмент также сопоставлен
с производственным replay положительного контроля: первые 30 одинаковых
попыток воспроизводят исходы, число соответствий, вероятность и каталожные ID.

На одной и той же попытке bootstrap, 30 центроидов, исходный FOV 25° ±8.75°,
текущая точка перебора 33.5°:

| Внутренняя проверка | До | После |
|---|---:|---:|
| Проецированные каталожные звёзды до ограничения 60 | 525 | 268 |
| Соответствия выбранной позе | 4 | 11 |
| Вероятность случайного совпадения | 1.4008e-2 | 1.2869e-13 |
| Неизменный порог | 1.0619e-9 | 1.0619e-9 |
| Результат tetra3 | отказ | проходит |

[Компактная внутренняя трасса](experiments/robustness-iteration-4-trace.json)
сохраняет каталожные ID этой пары проверок, покомпонентные исходы всех
целевых проверок, результаты 96 вызовов на вариант и хеши полных логов.
У исправленного варианта пять из 131 достигнутой проверки выбранной четвёрки
проходят прежний порог. Число проверок различается из-за более раннего успеха.

## Один ограниченный вариант

[Патч tetra3](../prototype/eval/tetra3_verify_footprint.patch) добавляет отсечение
проекций по прямоугольнику **перед** существующим ограничением 2N. Граница
расширяется на действующий радиус сопоставления, чтобы не терять допустимые
краевые пары. Полуширина и полувысота вычисляются из `pixel_scale` той же
попытки, по которому построены векторы детекций. Уточнённый по паттерну FOV
может отличаться; применять его к этим векторам было бы несогласованно.

В tracking уже существует аналогичное отсечение перед начальным подбором
пар. Оно не распространялось на общую последующую `verify_attitude`.
Исправление переиспользует этот принцип в общей проверке; оба вызывающих
пути передают свой масштаб. Новая маска неба, фильтр источников или иной
детектор не добавляются. Размер каталожного бюджета, допуски сопоставления,
формула вероятности, её порог, refinement и acceptance Starglyph не меняются.

Реализация находится в отдельной экспериментальной сборке. Патч применяется
к копии закреплённой версии зависимости; основной pipeline остаётся прежним.
Предварительный вариант использовал уточнённый FOV для границы. После ревью
эта несогласованность исправлена до окончательной фиксации; прежние измерения
сохранены отдельно и не смешиваются с итоговыми.

## Протокол сравнения

Оба варианта используют одинаковые 45 development-записей: 34 solver,
10 stress (восемь negative) и одну scene. Scene отмечается как пропущенная:
панорамная проекция вне протокола одной позы. Бюджет каждого вызова tetra3
2500 ms, предел процесса кадра 120 s; базы, параметры и порядок попыток
сохранены. Квантили и концентрационная эвристика предыдущих итераций выключены.

До запуска сохраняются хеши исходников, обеих сборок, баз, каталога,
изображений и защищённых JSON. Контрольный development-прогон выполнен
заново на неизменном основном бинарнике. Для окончательного исправления
переиспользуется этот проверенный контроль и повторяется весь вариант.
Тяжёлые проверки не запускались одновременно с измерениями.

Первый пробный запуск использовал незаполненный каталог cache изолированной
сборки. Его результаты исключены; исправлена ссылка на существующий общий
cache, после чего выполнены чистые измерения. Базы заново не подбирались.
Критерии до фиксации: сохранить прежние успешные solver-кадры, отклонить все
development-negative, не добавить ошибок процессов и wall-timeout; каждое
новое решение проверить по опорам вне списка подгонки. Время описательное:
один проход не даёт надёжной оценки ускорения.

Контроль воспроизводит все опубликованные статусы development. Единственное

растительности не объявлены звёздами. Проверка нового решения опирается
на 56 ранее просмотренных опор видимого неба, включая идентичности и края
поля из итерации 3. Среди них 26 отсутствуют в полном входном списке
Starglyph; дополнительно проверено расстояние до ближайшей входной детекции.

| Проверяемые опоры | Число | RMS, px | Максимум, px |
|---|---:|---:|---:|
| Все просмотренные | 56 | 3.03 | 7.88 |
| Вне входного списка Starglyph | 26 | 2.79 | 6.38 |
| Левые 10% ширины | 5 | 5.60 | 7.88 |
| Правые 10% ширины | 9 | 3.36 | 6.25 |

Отложенные опоры покрывают 94.8% ширины и 42.1% высоты кадра. Повторный
просмотр кропов показывает источники около предсказаний, в том числе у
краёв; крупные и асимметричные изображения звёзд ограничивают точность
центроидов. Нижняя часть закрыта растительностью. Это проверка на точках
вне подгонки, условная на просмотренных каталожных идентичностях, **не**
сертификация WCS всего кадра и не принятый ground truth.
[Покадровая геометрия](experiments/robustness-iteration-4-geometry.json)
сохраняет все измеренные/предсказанные позиции и происхождение точек.

Есть изменения прежних решений, которые нельзя скрывать общим solve rate:

| ID | Inliers до → после | Внутренний RMS, px, до → после |
|---|---:|---:|
| `wm_r_132162731` | 7 → 33 | 1.53 → 4.27 |
| `wm_r_143159342` | 27 → 18 | 3.00 → 3.41 |
| `wm_r_149276071` | 31 → 31 | 1.63 → 1.53 |
| `wm_r_180011612` | 27 → 30 | 0.99 → 1.25 |
| `wm_r_88363564` | 15 → 17 | 3.78 → 4.03 |

В `wm_r_143159342` выбирается более ранний default со списком 40 вместо
прежнего deep с 50 детекциями. Увеличение числа inliers в других случаях
не доказывает улучшение геометрии. Для большинства этих кадров внешнего
подтверждённого эталона нет. У `wm_r_149276071` RMS по четырём pending
внешним опорам улучшается 2.50→1.68 px, но расхождение моделей на сетке всего
кадра растёт 13.95→17.28 px. Четыре опоры и расхождение двух моделей не
позволяют установить истинную ошибку по всему полю. Это ограничение остаётся
причиной не включать эксперимент автоматически по одному solve rate.

## Итоговое holdout-сравнение

Holdout открыт только для окончательного измерения после development и всех
регрессионных проверок. Используются те же два бинарника, параметры и базы;
план отдельно фиксирует все 21 выбранное изображение и хеши до первого
запуска. Пакеты по шесть кадров чередуются между control и footprint.
Диагностика источников и подбор изменений на holdout, включая
`wm_r_146925915`, не выполняются. После начала этого сравнения алгоритм
и параметры не меняются.

Критерии заранее: сохранить прежние solver-успехи, отклонить отрицательный
кадр, записать все таймауты и ошибки. Новые статусы solved без просмотренного
внешнего эталона не объявляются подтверждённой геометрией. Один negative
не позволяет оценить частоту ложных принятий.

| Метрика holdout | Control | Footprint |
|---|---:|---:|
| Solver | 7/20 | 9/20 |
| Negative: корректный отказ | 1/1 | 1/1 |
| Потерянные прежние успехи | — | 0 |
| Ошибки процессов / wall-timeout | 0 / 0 | 0 / 0 |
| Таймауты отдельных попыток tetra3 | 24 | 16 |
| Сумма времени 21 запуска | 432.07 s | 392.39 s |
| Медиана времени | 16.43 s | 11.60 s |

Оба контроля — development и holdout — воспроизводят все опубликованные
статусы исходного baseline. Новые holdout-решения:

| ID | Детекции / inliers | Внутренний RMS, px | Независимая геометрия |
|---|---:|---:|---|
| `wm_r_112866114` | 50 / 15 | 2.95 | unresolved |
| `wm_r_63612482` | 40 / 13 | 1.47 | unresolved |

Эти два solved — результат неизменной проверки принятия Starglyph; без
внешней проверки их геометрическая правильность не объявляется доказанной.
У прежних успешных `wm_r_117897523` и `wm_r_59634605` также меняются выбранная
ветка и качество: соответственно 29→30 inliers / RMS 0.98→1.44 px и
16→26 inliers / RMS 1.47→3.57 px. Как и на development, это не одни и те же
наборы точек подгонки, поэтому сравнение внутреннего RMS не равно сравнению
истинной ошибки. Остальные исходы и все метрики сохранены в
[покадровом holdout-результате](experiments/robustness-iteration-4-holdout.json).
После просмотра этих итогов настройки не менялись и повторного прогона
для выбора параметров не было.

## Проверки и границы внедрения

[Машиночитаемый протокол проверок](experiments/robustness-iteration-4-checks.json)
содержит команды, статусы, длительности, хеши логов, кода и защищённых файлов.
Пройдены 97 core + 11 CLI Rust-тестов, отдельный ignored `extended_dense`,
92 Python-теста, Clippy core/CLI all-targets с `--no-deps -D warnings`,
форматирование workspace и проверка diff. Три существующих gates проходят:
CI на двух tetra3-снимках, smartphone 8/17 и sky-fill 13/17 с сохранением всех
12 обязательных прежних успехов. Последний использует **существующие ручные
маски**, поэтому его дополнительный успех не приписывается автоматической
маске неба и не прибавляется к основной коллекции.

Синтетический контроль содержит по 16 сочетаний условий на исходную и
исправленную версию. Без отвлекающих звёзд сохраняются все 12 опор; с 32
яркими источниками вне кадра исходная проверка теряет все, исправленная
сохраняет все 12. Краевой допуск и различие масштабов проверены отдельно.
Первая угловая проба оказалась вне неизменного кругового запроса; для проверки
именно прямоугольного отсечения она перенесена к середине края. Пороги и
алгоритм при этом не менялись. Для разных копий tetra3 следует использовать
отдельные Cargo target-каталоги: общий target однажды переиспользовал
непатченный fixture. После очистки tetra3 выполнена новая сборка и все
16 проверок исправленного варианта прошли. Производственные A/B-бинарники
изначально находились в разных target-каталогах.

Геометрическая область применимости патча ограничена текущим Starglyph:
его попытки создают центрированную pinhole-модель `CameraModel::from_fov`
с нулевым CRPIX и без предварительной дисторсии. Общий API tetra3 допускает
смещение оптического центра и undistort входных центроидов; в таких моделях
граница сенсора в пространстве проверяемых векторов уже может быть иной.
Их корректность этим экспериментом не проверена. Перед общим внедрением
в зависимость нужно либо явно ограничить исправление поддержанной моделью,
либо корректно перенести реальную границу сенсора через camera model и
проверить эти варианты отдельными тестами. Результаты текущего прогона
на такие конфигурации не распространяются.

Исходная версия зависимости, основной бинарник, Cargo.toml/Cargo.lock,
manifest, split/track, пиксели, опубликованный baseline и WCS-review
сохранены. Автоматическое изменение доступно как воспроизводимый патч и
изолированная сборка; оно не включено в основной продукт. Ограничение важно
из-за непроверенной геометрии изменившихся прежних решений, особенно
`wm_r_143159342`, и отсутствия принятого ground truth по всей области поля.

## Воспроизведение

Нужны прежние локальные изображения, каталог, готовые базы и артефакты
итерации 3. Python-геометрия требует NumPy, Astropy и Pillow. Все команды
ниже выполняются из `prototype/`; `TETRA3_SOURCE` указывает на локальный
исходник ровно tetra3 0.8.0 в Cargo registry. Инструмент проверяет SHA-256
исходного `solve.rs`; registry остаётся только для чтения.

```bash
ITERATION_OUT=artifacts/robustness-iteration-4-reproduction
python3 eval/tetra3_footprint.py prepare "$ITERATION_OUT" --registry "$TETRA3_SOURCE"
cargo build --release --offline --manifest-path "$ITERATION_OUT/pipeline/Cargo.toml" -p starglyph-cli
python3 eval/tetra3_footprint.py run "$ITERATION_OUT"
python3 eval/tetra3_footprint_report.py "$ITERATION_OUT" "$ITERATION_OUT/development.json"
python3 eval/tetra3_footprint_geometry.py "$ITERATION_OUT" "$ITERATION_OUT/geometry.json"
```

Обычный исполнитель ограничен development и не имеет режима автоматического
перехода на holdout. Он сохраняет план и измеренные входы, может продолжить
готовый префикс только при неизменных хешах. Для нового полного сравнения
нужен свежий каталог вывода. Состояние основного control-бинарника фиксируется
в протоколе, поэтому его следует собрать из текущего непатченного workspace
перед новым экспериментом.

Внутреннюю трассу воспроизводить в двух отдельных каталогах:

```bash
python3 eval/tetra3_internal.py "$ITERATION_OUT/trace-control" --registry "$TETRA3_SOURCE"
python3 eval/tetra3_internal.py "$ITERATION_OUT/trace-footprint" --registry "$TETRA3_SOURCE" --footprint
cargo build --release --offline --manifest-path "$ITERATION_OUT/trace-control/harness/Cargo.toml"
"$ITERATION_OUT/trace-control/harness/target/release/starglyph-tetra3-internal-trace" \
  artifacts/robustness-iteration-3/expanded/input.json "$ITERATION_OUT/trace-result.json" \
  2> "$ITERATION_OUT/trace.log"
cargo build --release --offline --manifest-path "$ITERATION_OUT/trace-footprint/harness/Cargo.toml"
"$ITERATION_OUT/trace-footprint/harness/target/release/starglyph-tetra3-internal-trace" \
  artifacts/robustness-iteration-3/expanded/input.json "$ITERATION_OUT/footprint-trace-result.json" \
  2> "$ITERATION_OUT/footprint-trace.log"
python3 eval/tetra3_internal_report.py "$ITERATION_OUT" "$ITERATION_OUT/trace.json"
```

Детерминированные проверки вызывают настоящую private `verify_attitude`
через исследовательскую точку входа в локальной копии. Это не переписанная
версия проверяемого алгоритма. В обеих ориентациях используются 12 звёзд,
с 32 более яркими внекадровыми источниками или без них, с краевой парой или
без неё, при одинаковом и различающемся исходном/уточнённом FOV.

```bash
python3 eval/tetra3_footprint_fixture.py "$ITERATION_OUT/fixture-control" --registry "$TETRA3_SOURCE"
python3 eval/tetra3_footprint_fixture.py "$ITERATION_OUT/fixture-patched" --registry "$TETRA3_SOURCE" --footprint
cargo run --release --offline --manifest-path "$ITERATION_OUT/fixture-control/Cargo.toml" -- \
```
